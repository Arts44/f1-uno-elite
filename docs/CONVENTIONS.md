## 1. What this project is / Ce que c'est

**F1 UNO Élite — Collection Tracker** is a 100 % client-side single-page PWA that lets a collector track their *F1 UNO Élite* trading-card collection: owned cards, doubles, wishlist, favourites, badges, titles and completion stats. **No backend, no database, no framework, no runtime dependencies.** State lives in the browser's `localStorage`; the app works fully offline once installed.

- **Live app:** https://arts44.github.io/f1-uno-elite/ (GitHub Pages, served static from `main`, root of `Collections/F1/`).
- **Repo:** `Arts44/f1-uno-elite` — the git root is the `Collections/F1/` folder, **not** the parent `ARC/` folder. All commands below assume you are in `Collections/F1/`.

🇫🇷 App 100 % côté client, hors-ligne, sans serveur ni framework. Le dépôt git est le dossier `Collections/F1/`. Toute progression est stockée dans `localStorage`.

## 2. HARD RULES — non-negotiable / Règles absolues

These are the rules that, if broken, ship a bug to production or violate the project's core promises. Treat every one as a blocker.

1. **Zero runtime dependencies. HARD RULE.** No npm packages, no CDN `<script>`/`<link>`, no framework, no SDK at runtime. The *only* dependency is `esbuild`, a `devDependency` used to bundle. Cloud calls use raw `fetch()` (no Supabase SDK). QR uses the vendored `qrcodegen.js`. Fonts are self-hosted WOFF2 — **never** add a Google Fonts request. If a task seems to need a library, stop and ask.
   🇫🇷 Aucune dépendance à l'exécution. Jamais de CDN, jamais de SDK. Seul `esbuild` (devDependency) est permis. Si une lib semble nécessaire → demander.

2. **All URLs must be relative. HARD RULE.** GitHub Pages serves from a sub-path (`/f1-uno-elite/`). Nothing may start with `/`. Every `fetch()`, asset href, `manifest.webmanifest` `start_url`/`scope`, and the service-worker registration/precache list uses `./` relative paths so the app runs identically at localhost, a domain root, and a sub-path. A leading-slash path is a bug.
   🇫🇷 URLs toujours relatives (`./`). Un chemin commençant par `/` casse GitHub Pages → c'est un bug.

3. **Rebuild the bundle after touching a bundled JS source. HARD RULE.** `app.bundle.js` (+ `.map`) is a **committed** artifact because Pages runs no build step. After editing any *bundled* root module, run `npm run build` and commit the regenerated bundle. The **bundled** sources are every root `*.js` **except** these classic (non-module) scripts, which are *not* bundled and need **no** rebuild: `sw.js`, `translations.js`, `data-embedded.js`, `card-descriptions.js`, `cloud-config.js` (and `app.bundle.js` itself). A local `.git/hooks/pre-commit` automates the rebuild, **but git hooks are not versioned** — after a fresh clone the hook is gone; recreate it or rebuild manually. Never commit a JS source change without the matching bundle.
   🇫🇷 Après édition d'un module *bundlé*, `npm run build` puis commit du bundle régénéré. Non-bundlés (pas de rebuild) : `sw.js`, `translations.js`, `data-embedded.js`, `card-descriptions.js`, `cloud-config.js`. Le hook pre-commit n'est pas versionné → le recréer après un clone.

4. **Bump `SW_VERSION` when any precached shell file changes. HARD RULE.** The service worker (`sw.js`) precaches the app shell **cache-first**. If you change any precached file (HTML, CSS, a bundled JS, a `data/*.json`, an icon, a font…) without bumping `SW_VERSION`, returning users keep the **stale** cached version. `SW_VERSION` is a single line near the top of `sw.js`. Bump it (e.g. `v37` → `v38`) on any release that alters a precached file, and confirm the precache list still lists every shipped shell file. **The new SW must stay in `waiting`** — never re-add `skipWaiting()` to the install handler: the in-app update banner (`update.js`) promotes it via the `SKIP_WAITING` message; auto-promotion would swap the shell under a running app. For a **user-visible release**, also add a `CHANGELOG` entry in `changelog.js` (that IS the app-version bump — `APP_VERSION` derives from the newest entry), with the change texts in all 7 languages.
   🇫🇷 **LE GARDE D'ÉTAT DE POSTE DE `livrer.sh` N'EST PAS UNE PARADE VERSIONNÉE.** Il refuse de livrer si le hook `pre-push`, `node_modules`, Playwright, son navigateur ou OpenCV manquent, avec la commande qui répare — mais il vit DANS le script, donc il ne protège que les livraisons qui passent par lui. Un `git push` direct depuis un poste neuf ne voit rien. C'est assumé et écrit sur place : le présenter autrement serait exactement le piège de ⑯. 🇫🇷 **« Release VISIBLE » veut dire visible PAR LE LECTEUR DU CHANGELOG, pas visible en général.** Le changelog est celui de l'APP, lu dans « Nouveautés » par des gens qui n'ouvrent jamais la vitrine : y annoncer un correctif de vitrine — décalage de mise en page, poids de la page d'accueil — serait une ligne fausse dans un fichier dont toute la valeur est d'être vrai. Un correctif de vitrine n'y entre pas, et n'entraîne donc pas de bump de version. Même raisonnement pour tout ce que l'utilisateur ne peut pas observer depuis l'app. Toute modif d'un fichier du shell précaché ⇒ incrémenter `SW_VERSION` dans `sw.js`. Ne jamais remettre `skipWaiting()` auto dans `install` (le bandeau de mise à jour le déclenche via message). Release visible ⇒ ajouter une entrée `CHANGELOG` dans `changelog.js` (c'est le bump de version), traduite ×7.

5. **UI text goes through i18n, in all 7 languages. HARD RULE.** Never hard-code user-facing text. Add a key and call `t('my.key')` (JS) or `data-i18n="my.key"` (HTML). Every new key must be added for **all 7 languages** in `translations.js`: `en, fr, es, zh, it, nl, de`. English is the fallback; an English-only string is an incomplete change.
   🇫🇷 Aucun texte d'interface en dur. Ajouter la clé dans `translations.js` pour **les 7 langues** (`en, fr, es, zh, it, nl, de`) et utiliser `t()` / `data-i18n`.

6. **Debug logging only through `logger.js`. HARD RULE.** Use `log()` / `warn()` from `logger.js`; they are gated behind `export const DEBUG = false` and are **no-ops in production**. Never leave raw `console.log` for debugging. Genuine, always-on error reporting (`console.error`, and `console.warn` for real warnings) is fine and expected. Ship with `DEBUG = false`.
   🇫🇷 Debug via `log()`/`warn()` de `logger.js` (no-op en prod, `DEBUG=false`). Jamais de `console.log` de debug résiduel. `console.error` pour les vraies erreurs = OK.

7. **Cloud config: anon key only, never `service_role`. HARD RULE.** `cloud-config.js` holds the Supabase `url` + `anon` public key. These are public by design (protected by Row Level Security server-side). **Never** put the `service_role` key anywhere in the repo — it bypasses RLS. `cloud-config.js` is a classic script (not bundled): editing it needs no rebuild. Empty both values to fully disable cloud.
   🇫🇷 `cloud-config.js` : uniquement l'`url` + la clé `anon` (publiques, protégées par RLS). **Jamais** la clé `service_role` dans le repo.

8. **Serve over HTTP — never `file://`. HARD RULE (for running/testing).** ES-module loading and `fetch()` of `data/*.json` are both blocked over `file://`. Always serve the folder over a local HTTP server before testing.
   🇫🇷 Toujours servir en HTTP local ; `file://` casse les modules ES et le `fetch` des JSON.

9. **Vider le cache AVANT de mesurer quoi que ce soit dans le navigateur. HARD RULE (pour vérifier).** Il y a **TROIS pièges**, et ils se découvrent un par un — cette règle a dû être corrigée trois fois :

   | Piège | Ce qui sert du périmé | Ce qui le perce |
   |---|---|---|
   | 1. Service worker | tout le shell précaché | `registration.unregister()` + `caches.delete()` sur chaque clé |
   | 2. Cache HTTP du **document** | `index.html` | rechargement avec une **URL modifiée** (`?v=<n>`) — `location.reload()` ne suffit pas |
   | 3. Cache HTTP des **sous-ressources** | `styles.css`, `app.bundle.js`, `translations.js`… | `fetch(f, {cache:'reload'})` sur **chacune** — changer l'URL du document ne les touche pas, elles ont leur propre entrée |

   La recette complète, dans cet ordre : **purger SW + `caches` → `fetch(…,{cache:'reload'})` sur les sous-ressources modifiées → recharger avec une URL modifiée.**

   **Le piège 1 ne s'arrête pas aux fichiers du dépôt.** Le service worker intercepte **toute** navigation dans sa portée (`./`) — y compris un fichier que tu viens de créer et qui n'a **jamais** existé auparavant. Une page de maquette écrite il y a deux minutes a été servie périmée : le SW répondait à sa place, et la page affichait une version antérieure d'elle-même. Le symptôme est déroutant (« mon `window.go` n'existe pas alors qu'il est dans le fichier ») et n'évoque pas le cache. **Avant de servir une page de travail temporaire, purge le SW** — ou sers-la depuis un autre port, hors de la portée.

   Pourquoi c'est une règle et pas un conseil : plusieurs mesures ont été prises sur du code périmé avant qu'on s'en aperçoive, et des conclusions ont dû être jetées. Une mesure faite sur un bundle obsolète ne se voit pas — elle a l'air juste.

   **Corollaire pour les mesures de mise en page :** `requestAnimationFrame` **ne se déclenche pas** dans un onglet ou un panneau masqué. Toute attente de stabilisation qui repose dessus ne stabilise rien et renvoie des valeurs oscillantes. Utiliser `setTimeout` seul.

   🇫🇷 Deux caches à purger : le SW **et** le cache HTTP. Purge SW + `caches`, puis rechargement avec URL modifiée. Et pas de `requestAnimationFrame` pour attendre la mise en page : il ne tourne pas dans un panneau masqué.

## 3. Stack & architecture

| Area | Choice |
|---|---|
| Language | Vanilla JavaScript (ES modules, ES6+), HTML5, CSS3 — no framework |
| Entry point | `app.js` (ES module): init sequence, global event wiring, SW registration |
| Build | esbuild → `app.bundle.js` (IIFE, minified, sourcemap). `npm run build` / `npm run dev` (watch) |
| Runtime deps | **None** |
| Storage | Browser `localStorage`, season-scoped keys |
| PWA / offline | `sw.js` (versioned precache, cache-first shell, stale-while-revalidate for external images) + `manifest.webmanifest` |
| Crypto | Web Crypto `SHA-256` (PIN); `CompressionStream` (backup codes) |
| QR | Vendored `qrcodegen.js` (Project Nayuki, MIT) — byte mode + SVG |
| Cloud (optional) | Supabase via **raw REST `fetch()`** (GoTrue magic-link auth); gated on `cloud-config.js` being filled |
| Tests | Node's built-in runner: `node --test` (no test framework installed) |
| Fonts | Self-hosted WOFF2 in `fonts/` (SIL OFL) |

**Two HTML entry points:** `index-dev.html` loads raw ES modules (no build needed — use for development); `index.html` loads the built `app.bundle.js` (production / Pages).

**Classic scripts loaded *before* the modules** (they set `window` globals the modules read): `data-embedded.js` (`window.__F1UNO_EMBEDDED`), `translations.js` (`window.__T` / `window.__BADGE_T`), `card-descriptions.js` (`window.__CARD_DESC`), and `cloud-config.js` (`window.__F1UNO_CLOUD`).

🇫🇷 JS vanilla en modules ES, point d'entrée `app.js`, bundle esbuild. Deux HTML : `index-dev.html` (modules bruts, dev) et `index.html` (bundle, prod). Quatre scripts classiques chargés avant les modules exposent des globals `window.__*`.

## 5. Conventions — how things are done here

**Event handling — delegation, not inline handlers.** User actions are wired through a single delegated listener in `app.js` on `[data-action="…"]` (and `[data-digit]`, `[data-card]`, etc.). To add an interaction: put `data-action="myAction"` in the HTML and add a `case 'myAction':` to the `switch` in `initEvents()`. **If the action writes to the collection, add it to the `VIEWER_BLOCKED` set** so viewer (read-only) mode blocks it. Avoid inline `onclick=`.
🇫🇷 Interactions via `data-action` + délégation dans `app.js`. Toute action qui **écrit** doit être ajoutée à `VIEWER_BLOCKED` (mode lecture seule).

**Module layout.** One concern per module (see the file map). Each file opens with a boxed banner comment (`══` border) naming its responsibility — keep that style. Imports are explicit named ES imports.

**i18n.** See Hard Rule 5. Badge texts live in `window.__BADGE_T`; card descriptions in `card-descriptions.js`.

**Rarity has two independent scales — do not conflate them.** (1) Card rarity is a **7-level** scale `epic · legendary · mythic · ultra · cosmic · divine · eternal` (no `common`/`rare` anymore), derived from role/champion base rarity with foil bonuses (+1 simple foil, +2 dual, +3 wild/promo/nitro, **clamped at `divine`**); owning a **complete set** (≥1 copy of every variant) raises the effective rarity by +1, clamped at `eternal` — so `eternal` is ONLY reachable via a complete set (in practice: champions). `divine` renders as an animated iridescent gradient; `eternal` as a black-gold animated chip with a golden tile glow, light sweep and ✦ sparks. (2) The **type-pill** colour/star ladder is a *separate* scale (`typeBadgeStyles` / `typeBadgeRarity` in `metadata.json`) and must not be changed when you touch card rarity. Any animation must respect `prefers-reduced-motion`.
🇫🇷 Deux échelles distinctes : la rareté de carte (7 niveaux `epic…eternal` ; set complet ⇒ +1, seuls les foils clampent à `divine`) et l'échelle des pastilles de type (`typeBadgeStyles`). Ne pas les confondre. Animations : respecter `prefers-reduced-motion`.

**`localStorage` keys.** Season-scoped **v2** format: `f1uno_owned_<year>`, `f1uno_badges_<year>`, `f1uno_auto_badges_<year>`, `f1uno_history_<year>`. Shared keys: `f1uno_theme`, `f1uno_lang`, `f1uno_font`, `f1uno_title`, `f1uno_onboarded`, PIN/viewer keys, backup-reminder keys, `f1uno_install_dismissed`, and `f1uno_cloud_session`. Legacy **v1** keys migrate automatically on load — don't break `migration`.
🇫🇷 Clés `localStorage` scoppées par saison (v2). Migration v1→v2 automatique : ne pas la casser.

**Code style & language.** 2-space indent, semicolons, single quotes. Existing code comments and `log()` strings are a **French/English mix** — that is fine; keep comments clear in whichever language fits, but **all identifiers and user-facing i18n keys stay English**.

**Commit messages — Conventional Commits. HARD RULE for git.** Format: `type(scope): subject`, lowercase type and scope, imperative, an em-dash (`—`) for the elaboration. Types in use: `feat, fix, docs, style, refactor, test, chore, build`. Real examples from this repo:
- `feat(cloud): step 1 — cloud-config.js (Supabase URL + anon key slots)`
- `fix(fonts): apply font vars inline via JS so a stale stylesheet can't break switching`
- `test: first unit-test suite — 65 tests over the browser-free logic`
- `docs: sync README with current app (fonts, rarity, collector tools, PWA, tests)`

🇫🇷 Commits en Conventional Commits : `type(scope): sujet` en minuscules, à l'impératif, tiret cadratin `—` pour préciser. Types : `feat, fix, docs, style, refactor, test, chore, build`.

### LIVRER — `scripts/livrer.sh`, jamais une chaîne de `&&` à la main

**Une règle qui ne tient pas après trois occurrences n'est pas une
règle, c'est une intention.** Trois fois un push est parti avec un
filet rouge, alors que la règle du code de sortie était écrite ici. La
parade est désormais MÉCANIQUE, en deux couches :

```bash
scripts/livrer.sh          # build → tests → lint → les trois filets navigateur
LENTS=0 scripts/livrer.sh  # sans les filets (commit de documentation seule)
```

**`livrer.sh` et `git push` s'enchaînent avec `&&`, JAMAIS avec `;`.** Quatrième occurrence, et la première où la parade mécanique existait déjà : `livrer.sh ; git push` a poussé `adba070` sur un rouge, le point-virgule jetant le code de sortie que tout le reste du dispositif s'emploie à produire. Le hook n'a rien vu — il ne bloque que sur `npm test` et `npm run lint`, par dessein. **La parade existait, son opérateur l'a contournée par inattention** ; et le rouge était de surcroît un FAUX rouge (registre ⑲), ce qui rend ce genre de contournement d'autant plus facile à se pardonner sur le moment.

`set -euo pipefail` : au **premier** code non nul, tout s'arrête. Le
script monte et démonte lui-même le serveur local sur 8123 — trois fois,
un filet a rougi parce que le serveur d'une session précédente était
tombé, un rouge qui n'accusait pas le produit.

**Et un hook `pre-push`** (installé par `scripts/installer-hooks.sh`,
versionné parce que les hooks ne le sont pas) qui **refuse** le push si
`npm test` ou `npm run lint` échoue — vu rouge au contrôle. Il ne lance
QUE le rapide (~26 s) : un garde de plusieurs minutes se contourne avec
`--no-verify`, donc il vérifie seulement que les filets lents ont laissé
leur **trace horodatée** sur le commit poussé (`.git/derniere-livraison`),
et le dit sans bloquer sinon. **Rapide toujours, lent tracé.**

### MESSAGES DE COMMIT — pas de trailer Co-Authored-By

**Les messages de commit ne portent pas de trailer `Co-Authored-By`.**
L'auteur des commits est configuré en noreply (`git config user.email`,
local au dépôt) ; le trailer est un mécanisme **SÉPARÉ** que GitHub lit
pour créditer un second contributeur, et le retirer de la configuration
d'auteur ne le retire pas du message. **Les deux se traitent
indépendamment.**

L'historique antérieur **n'est pas réécrit** : cinq tags, cinq releases
et le lien Codacy en dépendent, pour un gain nul.

> ⚠️ **La source de ce trailer n'est ni le dépôt ni git** — ni gabarit
> (`commit.template`), ni hook, ni consigne écrite ici : c'est
> l'environnement d'exécution de l'assistant qui l'ajoute par défaut à
> chaque message. Cette entrée existe pour que la consigne du mainteneur
> l'emporte explicitement sur ce défaut, plutôt que d'être réappliquée à
> chaque commit et corrigée à la main.

### VÉRIFICATION CODACY APRÈS PUSH

**Après chaque push, lancer l'analyse Codacy et rapporter le résultat.** Ne pas se contenter du dashboard, qui analyse en différé : utiliser la **CLI locale**, qui donne le résultat immédiatement sur le code qui vient de partir.

```bash
codacy repository gh Arts44 f1-uno-elite --reanalyze
codacy issues -o json          # le compte, après
```

**Trois issues de conduite :**

- **Nouvelle issue introduite par le commit** → la corriger dans un commit de suivi, **sans attendre qu'on le demande**.
- **Faux positif** → le marquer avec sa justification écrite (`codacy issue … -I -R FalsePositive -m "…"`), **jamais désactiver le pattern**. Doctrine établie : un pattern éteint cache aussi les vrais cas ; une issue marquée documente une décision. Reporter la même justification dans `.codacy.yml`, qui doit rester lisible sans accès au service.
- **Issue préexistante sans rapport avec le commit** → la **signaler**, ne pas la traiter dans la foulée.

**Rapporter systématiquement le nombre d'issues AVANT et APRÈS.** Un push qui augmente le compte sans que ce soit dit est un push qui **dégrade en silence**.

> ⚠️ **Si l'authentification CLI a expiré, LE DIRE** — ne pas sauter l'étape en silence. Une convention qu'on saute sans le dire est pire qu'une convention absente : elle fait croire à une vérification qui n'a pas eu lieu. C'est exactement le motif de `check_seed_honesty()`, qui plantait **avant** son rapport et laissait supposer un contrôle passé. Formulation attendue : « analyse Codacy NON faite — authentification CLI expirée », suivie de `codacy login`.

> **Deux pièges déjà payés.** ① Un marquage est attaché à un **emplacement**, pas à une décision : `SESSION_KEY` a rouvert en passant de `cloud.js:25` à `cloud-auth.js:34`. Après tout découpage qui déplace une ligne marquée, revérifier. ② Les patterns imposés par le **coding standard de l'organisation** ne peuvent être ni décochés ni désactivés au niveau du dépôt (`Pattern enforced by Default coding standard, can't be modified`) — le marquage occurrence par occurrence est alors le seul levier, et c'est une dette à écrire, pas un choix.

🇫🇷 Après chaque push : relancer l'analyse via la **CLI** (pas le dashboard), rapporter le compte **avant/après**. Nouvelle issue du commit → commit de suivi immédiat. Faux positif → marquer avec justification, jamais éteindre le pattern. Issue préexistante → signaler seulement. **Auth expirée → le dire, ne jamais sauter en silence.**

## 9. Gotchas — things that used to live only in the maintainer's head

- **The pre-commit hook is not in git.** After a fresh clone, nothing auto-rebuilds the bundle. Rebuild manually (or recreate the hook) or you'll commit a stale `app.bundle.js`.
- **Editing `translations.js` / `data-embedded.js` / `card-descriptions.js` / `cloud-config.js` / `sw.js` does NOT need a rebuild** — they're classic scripts outside the bundle. Editing any other root `*.js` **does**.
- **Stats progression history has no back-fill** — the curve starts empty the day the feature was installed. Don't try to reconstruct past data; there's no per-card timestamp.
- **`data-embedded.js` must stay in parity with the real `data/metadata.json`** (a few tests assert this) — it's the offline fallback.
- **Viewer mode** silently blocks write actions via the `VIEWER_BLOCKED` set in `app.js`; forget to list a new write action there and read-only mode leaks writes.
- **UN MEILLEUR RÉGLAGE DE QUALITÉ N'EST PAS UN GAIN : IL DÉPLACE LE CURSEUR SUR LA MÊME COURBE. CE QUI ROUVRE UN DOSSIER, C'EST CE QUI DÉPLACE LA COURBE.** La règle est née d'un chantier d'images — un encodeur candidat rendait 17 % d'octets en moins, et il les rendait en échange de fidélité, exactement comme l'aurait fait l'encodeur en place réglé plus bas. Mais elle ne vaut pas que pour les images : **c'est le motif de la moitié des faux chantiers de performance.** Baisser une qualité, réduire un nombre d'échantillons, raccourcir une durée, élargir une tolérance, sauter une vérification — tout cela « gagne » quelque chose, et tout cela se paie sur le même axe. Avant d'ouvrir un chantier de performance, poser la question : **est-ce que je propose un point différent sur la courbe existante, ou une courbe différente ?** Si c'est le premier cas, ce n'est pas un chantier, c'est un arbitrage — et il doit se présenter comme tel, avec les deux termes de l'échange chiffrés. Corollaire pour les mesures comparatives : deux candidats ne se comparent qu'à **qualité constante** ou à **octets constants**, jamais en laissant les deux bouger.
- **UN DÉFAUT PEUT VIVRE DANS LA TRANSITION, LÀ OÙ AUCUNE MESURE D'ÉTAT NE LE VOIT.** Famille distincte des instruments menteurs : ici l'instrument dit vrai, il regarde simplement au mauvais MOMENT. Vécu au signalement « la barre flottante masque les cartes » (1.72.0) : la mesure d'état — position du dernier bloc contre le haut de la barre, aux quatre tailles d'écran, iPad compris — répondait « rien n'est recouvert », et c'était exact **en fin de défilement**. Le défaut était PENDANT le défilement : la barre opaque tranchait net les lignes qui passaient dessous. Aucune mesure de repos ne pouvait l'attraper ; il a fallu **regarder une capture prise à mi-course**. **Règle : pour tout ce qui bouge — défilement, ouverture, transition, animation — mesurer AUSSI un instant intermédiaire, ou juger sur l'image plutôt que sur les nombres.** Corollaire : un utilisateur qui décrit un défaut « en enregistrant image par image » décrit très souvent un défaut de transition — le prendre au mot avant de conclure qu'il n'est pas reproductible.
- **« LA SUITE LOGIQUE » N'EST PAS UN ARGUMENT.** Une fonctionnalité se justifie par le besoin qu'elle sert, mesuré ou observé — jamais par la symétrie, la complétude ou l'élégance de ce qui existe déjà. **La question est toujours la même : quelle fonctionnalité ça débloque, et pour quel besoin ATTESTÉ ?** Quatre refus l'ont opposée, sur quatre sujets sans rapport : ① le découpage de `storage.js` (aucune fonctionnalité débloquée — le module était gros, pas bloquant) ; ② celui de `tutorial.js` (même mesure, même verdict) ; ③ une huitième langue (aucun utilisateur ne l'a demandée ; sept sont déjà à maintenir) ; ④ la fiche d'accord partageable du recoupement (le besoin observé — trois personnes s'échangeant des listes dans un fil — s'arrête à « voici l'échange » ; le protocole de réponse est une invention). **Corollaire : un refus se consigne AVEC son argument et sa condition de réouverture**, sinon il se rejoue dans six mois sous le nom de « la suite logique » — c'est-à-dire sans argument du tout. Les quatre sont dans `docs/POINTS-SIGNALES.md` et `docs/V2-REFACTOR.md`, chacun avec ce qui le rouvrirait : un retour d'usage réel, jamais une intuition de symétrie.
- **UN CONTEXTE « VIERGE » AU SENS DES DONNÉES N'EST PAS UN PREMIER LANCEMENT — et un élément PRÉSENT n'est pas un élément ATTEIGNABLE.** Deux moitiés d'une même règle, chacune payée séparément. ① Un `localStorage` vidé saute le choix de langue, la mise en route et la proposition de tutoriel : **toute fonctionnalité atteignable par un lien externe se vérifie depuis un profil qui n'a JAMAIS vu l'app**, ces trois écrans compris (`seed_jamais_lancee()` + `franchir_premier_lancement()` dans `capture_seed.py`, qui RENVOIE les étapes franchies pour qu'un test ne puisse pas passer au vert sans les avoir rencontrées). ② **Ce qui apparaît pendant la mise en route se vérifie en ATTEIGNABILITÉ, jamais en présence DOM** : `document.getElementById()` rend `true` pour un élément couvert par un écran de priorité supérieure — mesurer avec `elementFromPoint` sur la cible réelle. **TROIS fois payé** : les six défauts de l'état « 1 carte » (jamais rendu par une capture), la fiche d'échange perdue derrière la visite guidée, et le bandeau de mise à jour **présent 6 fois sur 6, atteignable 0 fois sur 6** derrière l'écran de langue — ce dernier ayant d'abord donné un faux « 10/10 » à un banc qui interrogeait le DOM. La règle du moment vit dans `app/moment.js`, partagée : une surcouche ENREGISTRE toujours, et ne diffère que l'affichage.
- **SOUPÇONNER L'INSTRUMENT AVANT LE PRODUIT.** C'est UNE règle, pas une collection d'anecdotes : quand une mesure accuse le code, elle énonce une hypothèse, pas un verdict. Avant de corriger quoi que ce soit, faire rendre à l'instrument le cas RÉEL et vérifier qu'il sait le mesurer. **Ordre de suspicion : l'instrument, puis la chaîne (bundle reconstruit ? cache purgé ? bon fichier ?), puis le contrôle, et le produit en DERNIER.** La règle a dix-huit façons connues de se manifester — les reconnaître fait gagner l'exécution qui les démasque, mais c'est la règle qu'on retient, pas la liste : ① **la condition de rendu n'est pas celle du terrain** (un banc de lisibilité à densité 3 « prouvait » qu'aucun trait fin ne survit à 14 px — faux à densité 1, la densité réelle) ; ② **l'API répond à côté de la question** (`getBBox()` sur un `<use>` rend 0…120 sur un tracé qui n'occupe pas son cadre — mesurer au raster) ; ③ **la donnée de test est dégénérée** (un motif répétitif, `'A'`×700, trompe un détecteur qui marche très bien sur une charge réelle) ; ④ **on mesure un état de repos alors que le défaut vit dans la TRANSITION** (« rien n'est recouvert » était exact en fin de défilement et faux pendant — voir l'entrée dédiée ci-dessous) ; ⑤ **on lit la sortie d'une commande sans lire son code de sortie** (un `grep` ou un `| tail` renvoie 0 et laisse passer un échec — voir l'entrée dédiée). **CE CAS-CI SE REPRODUIT PLUS QUE LES AUTRES, ET PAS POUR LA MÊME RAISON** : ce n'est pas un défaut de raisonnement, c'est un réflexe de frappe — `commande | tail -3 ; echo $?` s'écrit tout seul, et la parade demande de penser à quelque chose au moment précis où la main tape vite. Une parade ne corrige pas un réflexe. **PISTE, NON FAITE : en faire un outil plutôt qu'une règle** — un alias ou une petite commande du dépôt qui exécute, capture la sortie dans un fichier ET rende le vrai code, de sorte que la forme naturelle soit aussi la forme juste. À chiffrer le jour où ce cas se reproduira encore ; c'est la même logique que ⑰, où une parade qui échoue plusieurs fois appelle un mécanisme et non une meilleure formulation. ; ⑥ **le harnais de rendu n'a été exécuté que dans UN ordre d'insertion** (deux surcouches à `z-index` égal : le test d'atteignabilité interroge celle qui est arrivée en dernier, conclut « atteignable », et ne voit jamais que l'autre est intégralement recouverte — POINTS-SIGNALES n°24). **Parade : tout test de coexistence de surfaces s'exécute dans LES DEUX ORDRES**, et mesure l'atteignabilité des DEUX surfaces, pas seulement de celle qu'on soupçonne. ; ⑦ **un harnais refait rend des chiffres qu'on ne réconcilie pas avec la campagne précédente** (la même paire mesurée à 47 px puis à 30 px : aucun des deux relevés n'était faux — le premier portait un contenu de toast synthétisé plus long que le contenu réel, et le changement d'instrument n'avait pas été déclaré. Un écart non expliqué se lit comme une correction silencieuse d'un chiffre publié). **Parade : toute mesure qui en remplace une autre cite l'ancienne, donne le nouveau chiffre, et EXPLIQUE l'écart — un chiffre qui bouge sans raison écrite invalide les deux.** **Et la parade vaut À L'INTÉRIEUR d'un même rapport, pas seulement d'une campagne à l'autre** : un écart de coût annoncé entre deux options se recalcule poste par poste avant d'être écrit — un chiffre asséné qui porte une recommandation est pire qu'un chiffre absent. **TROIS RÉCIDIVES APRÈS L'ÉCRITURE DE CETTE PARADE, ET C'EST LA DONNÉE QUI COMPTE :** un rapport annonçant « 9 lignes » sur un périmètre, un livrable comparant −12 à +62 sur deux jeux de postes, et la comparaison de `styles.css` elle-même — deux jeux de postes, encore. **Les trois ont été relevées par le mainteneur, jamais par l'auteur du chiffre.** Une parade que son auteur n'applique jamais n'est pas une parade : c'est une intention. D'où le passage de l'intention au MÉCANISME, et il ne se déclenche pas à la relecture mais **AU MOMENT DE RENDRE LE CHIFFRE** — poste de vérification obligatoire, au même titre que le contrôle négatif sur un garde : **tout chiffre comparé à un chiffre antérieur DÉCLARE EXPLICITEMENT SON PÉRIMÈTRE, et les deux périmètres sont MONTRÉS CÔTE À CÔTE.** Pas « j'ai vérifié que c'est comparable » — les deux périmètres écrits, l'un sous l'autre, dans le rapport que le lecteur a sous les yeux. Un chiffre dont le périmètre n'est pas écrit à côté de celui auquel on le compare ne se rend pas : il se recalcule ou il se tait. ; ⑧ **on rapporte une ABSENCE sans avoir prouvé que la chose avait le droit d'apparaître** (« badgeToast : ABSENTE » n'était pas un fait du produit mais un ordre d'appel du harnais — `_drainToastQueue()` diffère de 1200 ms quand le toast standard est déjà là). **Parade : une absence n'est un résultat qu'accompagnée d'un CONTRÔLE POSITIF — la même surface obtenue dans les conditions où elle doit paraître.** C'est le pendant exact du contrôle négatif exigé sur les gardes. **TROISIÈME RÉCIDIVE, 21/08/2026, et une variante qui mérite sa propre parade :** affirmation que « 44 n'apparaît nulle part » pour Lewis Hamilton, tirée d'une lecture du champ `number` des cartes — qui vaut 31, 32, 33 et porte le rang dans le set, pas le numéro de course. **Le 44 existait, ailleurs sur le chemin de rendu** : `metadata.json → driverNumbers`, indexé par NOM de pilote, lu par `DRIVER_NUMBERS[card.name]?.n`. L'utilisateur avait sous les yeux quatre contre-exemples à l'écran (#001 Albon 23, #004 Alonso 14, #007 Antonelli 12, #010 Bearman 87) qui suffisaient à réfuter l'affirmation, et je ne les avais pas cherchés. **Parade spécifique : pour une absence dans l'AFFICHAGE, c'est le CHEMIN DE RENDU qu'on suit, pas le champ de données qui semble porter le nom attendu.** Partir de ce qui est peint, remonter au code qui le peint, puis seulement aux données — l'inverse conclut sur le premier champ dont le nom ressemble. ; ⑨ **on simule le geste au lieu de le faire** (`element.click()` déclenche le gestionnaire QUELLE QUE SOIT la valeur de `pointer-events` : il n'y a aucun test de survol. Un filet qui vérifiait qu'aucun clic ne passe sous un voile en comptait six, avec un CSS parfaitement correct — l'instrument accusait le produit). **Parade : un geste se joue au niveau du DISPOSITIF — la souris à des coordonnées, le clavier par des touches — jamais par l'API qui court-circuite la couche qu'on prétend tester.** Bonne nouvelle enfouie dans ce cas : c'est le CONTRÔLE NÉGATIF qui l'a démasqué, en refusant de rougir là où il devait. Un contrôle négatif ne vérifie pas seulement le garde, il vérifie l'instrument. ; ⑩ **on mesure la BOÎTE et pas le CONTENU** (une surface peut faire 351 px de large pendant que son bouton est à x=470 sur un écran de 375 : un conteneur ne rétrécit pas ce que `min-width:auto` l'empêche de rétrécir. Le filet rendait vert sur des boutons hors écran). **Parade : tout contrôle de géométrie descend jusqu'aux DESCENDANTS — bornes de l'écran, chevauchements, atteignabilité — parce qu'un parent conforme ne prouve rien de ses enfants.** ; ⑪ **la donnée de test est un GABARIT MAL SUBSTITUÉ** (le contenu synthétique d'un badge-toast, dont les expressions imbriquées n'avaient pas été remplacées, produisait un libellé plus court que le vrai — donc une surface plus BASSE que la vraie, donc une scène plus facile que la réalité). **C'est une RÉCIDIVE de ⑧, et il faut dire pourquoi la parade ne l'a pas empêchée : ⑧ était écrite pour les ABSENCES (« prouver que la chose avait le droit de paraître »), et ici la chose était bien là — seulement fausse. Une parade formulée sur le symptôme qu'on venait de vivre ne couvre pas la variante d'à côté.** Parade élargie, et c'est la formulation qui compte : **présent ne veut pas dire conforme. Le contrôle positif porte sur le CONTENU RÉEL — les vraies chaînes, dans les vraies langues — et un instrument neuf hérite des parades des instruments précédents avant sa première exécution, pas après son premier mensonge.** ; ⑫ **on prend « absent de mon contexte » pour « inexistant »** — c'est ⑧ appliqué à sa propre mémoire, et c'est le cas le plus facile à commettre parce qu'il ne ressemble pas à une mesure. Vécu à la fin du chantier de la zone basse : affirmation qu'une section n'avait jamais été écrite, alors qu'elle l'avait été et que l'utilisateur en détenait le texte — la conversation avait simplement été résumée entre-temps. Une absence conclue **sans contrôle positif**, exactement comme ⑧, à ceci près que la chose manquante était un souvenir. **Parade : avant d'affirmer qu'une chose n'a pas été écrite, la CHERCHER dans l'historique — transcription, journal git, fichiers de session. Et à défaut de preuve, dire « je ne le retrouve pas » et non « ça n'existe pas » : les deux phrases n'engagent pas la même chose. LE FIL DE L'UTILISATEUR FAIT FOI SUR MA RECONSTRUCTION**, toujours, y compris quand ma reconstruction est confiante — la confiance est ici l'exacte mesure du danger, puisqu'un contexte résumé ne signale pas ce qu'il a perdu. ; ⑬ **on SAUTE un contrôle d'instrument parce qu'il a déjà été passé une fois.** La justification a l'air raisonnable — « ce fait est consigné, le refaire coûterait une exécution pour rien » — et elle est fausse : un contrôle d'instrument ne mesure pas le monde, il mesure L'INSTRUMENT, et l'instrument d'aujourd'hui n'est pas celui d'hier. Version du navigateur, du pilote, du serveur de test, une dépendance qui a bougé : le fait consigné peut rester vrai pendant que le harnais, lui, a changé d'état. **C'est ⑦ appliqué aux instruments et non aux chiffres : on ne réutilise pas une calibration sans la refaire, comme on ne réutilise pas un chiffre sans redéclarer son périmètre.** Parade : **un contrôle d'instrument se rejoue à chaque campagne, même quand on connaît sa réponse — et surtout quand on la connaît**, puisque c'est le seul cas où l'on serait tenté de ne pas regarder le résultat. Un contrôle dont on prédit l'issue sans l'exécuter n'a pas été fait. ; ㉕ **DANS UNE COMPARAISON, LA RÉFÉRENCE DOIT ÊTRE À ÉGALE DISTANCE DES DEUX TERMES.** À distinguer de ⑦, qui porte sur les PÉRIMÈTRES déclarés, et de ㉔, qui porte sur ce qu'un contrôle exerce : **ici les deux périmètres étaient identiques et le contrôle était juste. C'est la CHAÎNE DE PRODUCTION des termes qui était asymétrique.** Vécu sur les captures de la vitrine : tous les candidats de compression étaient encodés depuis le JPEG, et la référence de la mesure ÉTAIT ce JPEG — tandis que le fichier en place, lui, venait du PNG de capture. Le réflexe coûte une exécution et évite une heure de recherche d'une cause qui n'existe pas. Il vaut pour toute mesure bruitée : captures, temps de rendu, taille de bundle.
- **Le bundle IIFE MASQUE les symboles oubliés lors d'un déplacement de code. `npm run lint` les attrape ; le navigateur reste nécessaire pour le RESTE.** Vécu pendant le découpage de `badges.js` : cinq symboles (`DAY_MS`, `autoBadgeUnlocked`, `_bt`, `badgeDifficulty`, `difficultyLabelKey`) sont restés dans le module d'origine alors que le code qui les utilise avait déménagé. `npm run build` passait, `npm test` passait — **955 tests verts** — parce qu'esbuild en `--format=iife` met tout dans une portée unique, où un symbole « manquant » reste visible. En modules bruts (`index-dev.html`), c'est un `ReferenceError` immédiat. **Depuis 1.60.2, `npm run lint` (règle Biome `correctness/noUndeclaredVariables`, bloquante en CI) détecte cette classe entière en 40 ms** — elle a trouvé deux des cinq du premier coup, que ni les tests ni une vérification navigateur manuelle n'avaient vus, parce que personne n'avait ouvert le sélecteur de titres. **Ce que le lint NE voit PAS, et qui garde donc sa vérification navigateur** : le rendu (rien ne dit qu'une modale s'affiche correctement), les chemins qu'aucun test n'emprunte et dont la panne n'est pas un symbole manquant, et tout ce qui dépend d'un état d'exécution. **Règle pratique : après un déplacement entre modules, `npm run lint` d'abord — c'est instantané et exhaustif sur sa classe — puis `index-dev.html` pour exercer ce qui se voit.**
- **Un déplacement de code produit DEUX erreurs symétriques, et un seul garde n'en voit qu'une.** Le premier garde (`noUndeclaredVariables`) attrape le symbole **utilisé sans être importé**. Il ne peut rien dire du symbole **importé sans être utilisé** — il regarde dans l'autre sens. Le découpage de `badges.js` a produit les deux : cinq du premier type, **dix-neuf du second**. Codacy en a signalé onze ; Biome a trouvé les huit autres. **Depuis 1.60.3, `npm run lint` arme les deux règles** (`noUndeclaredVariables` + `noUnusedImports`), toutes deux bloquantes en CI. **Pourquoi `noUnusedImports` et pas `noUnusedVariables`** : cette dernière compte 56 constats dont **54 sont des `catch(e)` muets** — une étape rouge en permanence apprend à ignorer le CI. Les imports, eux, sont à zéro : le garde peut être bloquant sans jamais mentir. Le reste du bruit reste sur l'étape informative. **Un import mort n'est pas cosmétique** : il maintient une arête dans le graphe d'imports. Les dix-neuf de `badges.js` retiraient à eux seuls l'arête `badges.js → storage.js` et **trois arêtes sur 128** (128 → 125), sans qu'une ligne de logique bouge.
- **Une valeur qui ressemble à un hack peut être une correction. Lire son commentaire avant de la retirer.** Vécu au recentrage du casque (1.63.1) : le bloc monogramme des cartes écurie porte un `translateY(-18px)` qui a toute l'allure d'une rustine d'alignement — c'est en fait la **parade minimale mesurée** à une collision entre le nom d'écurie (2 lignes) et le bouton « + » (débordement de +10 à +17 px si on centre, mesuré sur les 9 écuries). Le retirer « en même temps que le centrage », comme le prévoyait le plan, aurait réintroduit un bug déjà payé et documenté sur place. **Réflexe** : avant de supprimer une valeur étrange, lire le commentaire qui la porte — et s'il n'y en a pas, la mesurer ; la différence entre un hack et une correction, c'est qu'une correction a une raison qui tient encore.
- **Un banc de lisibilité doit rendre à la DENSITÉ où le problème se pose, pas à celle qui flatte le tracé.** Vécu au choix du casque (1.63.0) : le banc à densité 3 montrait qu'« aucun trait fin ne survit à 14 px » — bouillie nette, trois candidats éliminés. À **densité 1** — celle des écrans où le 14 px se pose réellement — l'anticrénelage fait FUSIONNER les traits en une masse qui garde le profil : le problème n'existait pas. L'instrument mentait avant la conclusion, dans les deux sens possibles : une densité haute préserve les détails (flatte un tracé fin, cache qu'une masse boucherait), une densité basse les fond. **Règle : rendre aux densités RÉELLES des contextes visés (1 ET 3), et juger chaque taille à la sienne.** Corollaire déjà payé ailleurs : les pixels se comparent grossis au plus proche voisin, jamais lissés. Même famille, payée au centrage du casque : `getBBox()` sur un `<use>` a rendu 0…120 sur un tracé qui n'occupe pas tout le cadre — quand l'instrument peut mentir, mesurer au RASTER (bornes et centroïde d'encre, pixel par pixel).
- **Un contrôle négatif qui passe au VERT doit être suspecté AVANT le garde.** Le contrôle obligatoire d'un garde est de le voir échouer (casser la chose protégée → rouge). Mais quand ce contrôle **passe au vert**, le réflexe est de conclure « le garde est mauvais » — et c'est souvent faux : c'est **la chaîne entre la modification et la vérification** qui est cassée. Vécu deux fois avec la même cause : `app.bundle.js` non reconstruit. ① Une vérification navigateur sur `index.html` validait un code que le bundle ne contenait pas encore ; ② un contrôle négatif de `verify_tutorial.py` (clé retirée de `tutorialKeys()`) est passé au vert parce que le script lit `index.html`, donc le bundle, et la modification n'y était pas. Même famille que le piège `--format=iife` : le bundle masque ce qu'on croit avoir changé. **Ordre de suspicion** : 1. la modification atteint-elle ce que la vérification lit (bundle reconstruit ? cache purgé ? bon fichier ?) — 2. le contrôle casse-t-il vraiment la chose protégée — 3. alors seulement, le garde. Variante de la même famille : un fragment cherché qui diffère par un caractère invisible (apostrophe typographique `’` contre ASCII `'`) fait tomber la vérification dans la mauvaise branche sans erreur.
- **Un garde-fou doit s'ancrer sur du CODE, jamais sur de la prose — il ignore les commentaires.** Vécu **deux fois en une session**, ce qui en fait un motif et non un accident. Un test cherchait `exception when others then return new` dans `db/03-functions.sql` : il passait au vert **après suppression du bloc qu'il protège**, parce qu'il trouvait la formule dans le **commentaire qui la décrit** juste au-dessus. Même famille : un test de markup satisfait par le commentaire d'exemple placé à côté. La doc d'un fichier cite toujours ce que le fichier fait — c'est même sa raison d'être — donc chercher une formule « quelque part dans le fichier » revient à vérifier que la documentation existe. **Parade** : filtrer les lignes de commentaire avant de chercher (`.split('\n').filter(l => !l.trimStart().startsWith('--'))`), et ancrer le motif (`/^…/m`) plutôt que de le laisser flotter. **Contrôle obligatoire** : supprimer le code visé et vérifier que le test devient rouge. Un garde qu'on n'a pas vu échouer n'a pas été vérifié, il a été espéré.
- **Ne recliquez pas la navigation pour « forcer » l'affichage d'une vue.** Les transitions entre vues (1.32.0) ont une durée ; un clic pendant la transition la **relance depuis le début**. Un script d'automatisation qui cliquait sur l'onglet Stats toutes les 200 ms tant que la vue n'apparaissait pas ne l'a **jamais** fait apparaître — chaque clic annulait le précédent, et le symptôme (« la vue ne s'affiche pas ») ressemble à une panne, pas à un excès de zèle. **Un seul clic, puis attendre** (~1,5 s suffit ; poller l'apparition du contenu, pas recliquer).
- **Ne sondez pas les modules bruts depuis `index.html`.** Un harnais qui fait `await import('./cloud-sync.js')` dans la page **de production** charge une **SECONDE copie** du graphe de modules — la page tourne déjà sur `app.bundle.js` — et la ré-exécution d'`app.js` casse sur une initialisation circulaire (`Cannot access '_authenticated' before initialization`). Le symptôme ressemble à un défaut du produit ; ce n'en est pas un, personne ne charge le bundle ET les modules bruts ensemble. **Sonder depuis `index-dev.html`**, où `import()` rend les mêmes instances que la page. Corollaire : le SEED de `capture_screenshots.py` injecte une **session cloud fictive** (`f1uno_cloud_session`) pour les captures — la retirer du contexte avant tout test cloud réel, sinon elle masque la vraie session.
- **Arc browser** hides behind a Chrome UA and has no install support; `install.js` detects it via `--arc-palette-*` CSS vars and shows an honest message. Don't "simplify" that away.
- **Driver-number fonts** (Orbitron / Racing Sans One) are intentionally fixed and must **not** follow the font-theme picker.
- **Colour/contrast:** stat and rarity palettes are contrast-checked in **both** light and dark themes. If you change chart/tile/rarity colours, re-check contrast in both themes (the `dataviz` skill provides a palette-contrast validator; there is no such script committed in this repo).

## 10. When unsure / En cas de doute

Ask the maintainer before: adding any dependency or CDN; changing the rarity scales, the storage key scheme, or the migration; altering the service-worker caching strategy; or making an irreversible data change. Prefer a small, tested, reversible change over a clever large one. Preserve the honest, precise tone of the existing code and docs.

🇫🇷 Demander avant : toute dépendance/CDN, tout changement des échelles de rareté, du schéma de clés `localStorage`, de la migration, ou de la stratégie de cache du service worker. Préférer une petite modif testée et réversible. Conserver le ton honnête et précis du code et de la doc existants.
